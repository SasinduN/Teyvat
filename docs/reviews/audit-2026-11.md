# Bug and performance audit, November 2026

Branch `fix/audit-2026-11`, 14 November 2026. The backlog's "Bug and performance audit", before the
Railway project transfer.

## How it was measured

- **Locally only.** Nothing was run against production. The built site (`npm run build && npm start`)
  on the local dev database (`teyvat_dev`, every migration to 0026), with Galle's four researched
  attractions published (the same four the tests use), so `/destinations/galle` has its Nearby section.
- **Lighthouse 12.8.2, mobile** (its defaults: a Moto G-sized screen, 4× CPU slowdown, a simulated slow
  4G), Chrome 157, headless, one run per page. TBT moves by 100 ms or more between runs on this laptop;
  read single numbers with that in mind.
- **Layouts:** a script in headless Chrome at 320, 375, 768 and 1280 px, light and dark, with a saved
  wishlist: text and boxes past the edge of the screen, the number of `h1`s, console errors and warnings,
  failed requests, layout shifts (`PerformanceObserver`, buffered), and every internal link it found
  (fetched, redirects not followed).
- **What local can't show:** the local database has no R2 photo sets, so every photo is the seed's
  Unsplash URL at full size (186 to 424 KB for a header photo), with no `srcset`. Production serves R2
  files from 480 px wide on phones. Local LCP is therefore pessimistic for photo-led pages. To measure
  production, see the last section.

## Fixed in this PR

1. **The `<body>` layout shift** (backlog). The page header (`.te-page-hero`) has an 80 px top margin to
   start below the fixed header. With nothing between them, that margin collapsed through `main`,
   `.site` and `#root` into `<body>`. While a page's code loads, its placeholder has no margin, so when
   the page arrived the whole body moved 80 px down: CLS 0.100 on a phone, on every page but the home
   page (whose hero has no margin). `.site main { display: flow-root; }` (`src/index.css`) keeps the
   margin inside `main`. The page looks the same once loaded; the placeholder no longer jumps. CLS is now
   0 on every page measured.
2. **Compression.** `/api/content` and the page shell went out uncompressed. `server/src/compress.ts`
   sends them as Brotli (quality 5) or gzip, with Node's own zlib and no new dependency. Express's ETag
   is over the compressed bytes, which are the same each time, so revalidation still gets its 304.
3. **`/api/content` preloaded.** It used to start only after the 107 KB entry had loaded and run. Every
   public page's head now has `<link rel="preload" href="/api/content" as="fetch" crossorigin>`, and the
   app's fetch gets that response: one request, not two. The admin's pages don't have it.
4. **The header photo preloaded on more pages.** The home page already preloaded its first slide. Now so
   do the other pages whose header shows their share image: the list pages, Plan, Photo credits, the
   wishlist, and every destination, tour, article and experience. Each uses the same `srcset` and
   `sizes` as the header, so it is one download. About is left out (its header is the second slide).
5. **Accessibility.** `/destinations` and `/journal` skipped a heading level (98): a hidden `h2` before
   the destination cards, and the photo story captions are `h3`, not `h4`, with the same classes and look.
   The map search's submit button reads "Explore" but was named "Search destinations"; it's now
   "Explore destinations", so its name contains the visible word (label in name).
6. **`browser-hero-contrast` (backlog: "watch it for flakiness").** Found: it decoded each screenshot with
   an `<img>`'s `decode()` in a background tab, and headless Chrome can leave that pending. On this laptop
   it hung every run, on `main` too, until the 60 s limit. It now decodes with `createImageBitmap`, as the
   pixel tests do: 3 runs out of 3 pass in 23 s. The check itself (the same pixels, the same AA thresholds)
   is unchanged.

`server/test/browser-preload.test.ts` covers 1 to 4: one request for `/api/content`; on 14 page types,
the preloaded photo is the photo shown and is fetched once; no layout shift at 375 or 1280 px as a page
arrives; compression, `Vary`, and a 304.

Screenshots (`npm run screenshots -- --base origin/main`, light and dark, phone and laptop, the home page,
`/destinations`, Galle, `/explore`, `/tours` and `/journal`): 12 of 24 pairs identical. The rest differ by
0.00 to 0.04% of pixels (map markers nudged a pixel, image decoding), except Explore on a phone in dark,
3.3%: Kudumbigala's photo, which is one of the two dead Unsplash photos below and loaded in one build and
not the other. No visual change.

## Checked, nothing to fix

- **The floating-booking and WhatsApp flakes** (backlog). `browser-floating-booking` passed 3 runs out of 3,
  and `browser-whatsapp` 3 out of 3, locally. In CI, the last `browser-whatsapp` failures were on 13 and
  14 October ("hidden while the enquiry form is open": an element not there yet), before the floating
  buttons were rewritten in #55. None of the latest 60 CI runs failed on either. Suggest closing both
  backlog items if they stay quiet until launch.
- **The booking flow** with `BOOKINGS_ENABLED=true`: `browser-bookings` passes (8 of 8), no overflow at any
  width in either theme, no console errors, every link on it 200, accessibility 100.

## Left, with reasons

| What | Why it's left |
|---|---|
| **Mobile performance under 90** (64 to 88 locally) | LCP waits on the client: the 107 KB entry has to load and run (590 to 990 ms of CPU at Lighthouse's 4× slowdown), then render the header from `/api/content`. On the home page the LCP is the headline itself, with 4.8 s of render delay. What would move it is rendering each page's header in the HTML on the server, or a smaller entry (Framer Motion's `MotionConfig` sits in `PublicLayout`, so it's in the entry). Both are changes of architecture, each needing its own plan and screenshots. Local photos are also full-size Unsplash files with no `srcset`, so production should score better: please measure it (below) before deciding. |
| **Two dead seed photos** (404 at Unsplash) | `photo-1608933221980-dfc7dd884fbf` (the Jaffna cover, the "Hidden Sri Lanka" experience category, a hidden gem, a journal article, a photo story) and `photo-1581852017103-68accd5509b6` (the Udawalawe cover, Kudumbigala's hidden gem). The Jaffna and Udawalawe covers are pinned to R2 copies in production (`shared/public-photos.ts`). Whether production's other rows still use these URLs couldn't be checked from here. A replacement has to show the right place, so it's a content decision: in Admin, look at those rows and upload a photo through Media. |
| **`/booking?tour=…` shifts** (CLS 0.24 to 0.31 in the layout script; 0 in Lighthouse, whose timing let the catalog arrive first) | While the catalog loads, the page is one line ("Loading destinations and vehicles…"), so "My requests" sits high on screen; the form then pushes it below the fold. Bookings are off in production, and the booking fixes are Sasindu's list in the backlog. A fix: render "My requests" only once the catalog has loaded, or give the loading state the form's height. |
| `theme-init.js` render-blocking | On purpose: it sets the theme before the first paint (no flash). 2 KB, same origin. |
| `theme-init.js` cached for an hour | It isn't content-hashed, so a longer cache would keep an old copy after a deploy. |
| Links without `href` (Lighthouse SEO, "crawlable anchors") | On purpose: a site-settings link that isn't set renders without `href` (migration 0004). They disappear once the owner fills them in. |
| Four DM Sans weights downloaded | 15 KB each, self-hosted; only 400 is preloaded. The design uses all four. |

## Measuring production

Read-only, and only if you want to. Page loads, like any visitor's; nothing touches the database.

```bash
# Each page, mobile, as above (no install: npx downloads Lighthouse once)
npx -y lighthouse@12.8.2 "<site URL>/" --only-categories=performance,accessibility --quiet --chrome-flags="--headless=new" --output=json --output-path=./lh-home.json
# The same for /explore, /destinations, /destinations/galle, /tours, /tours/<a tour>, /when-to-go, /wishlist, /journal
```
